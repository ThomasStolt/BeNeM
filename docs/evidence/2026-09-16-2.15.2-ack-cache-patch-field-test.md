## What was being tested

2.15.2 changes behaviour in exactly one situation: an **acknowledgement arriving for an incident
the maintenance cache has not yet seen** — an ACK inside the first ~120 s cache cycle of the
incident. Before 2.15.2 the override was recorded nowhere and dropped silently
(`note_state_override_any_server()` returned 0 and `main.py` logged only `if n:`), so the incident
flipped back to **OPEN** on the next poll. That path had **never been exercised in the field**:
across the whole persisted log, `Cache patched` had appeared three times and every one was
`-> CLOSED`, never once `-> ACKNOWLEDGED`.

## Observations during the run, none of them 2.15.2

Recorded here because they were found during this test; each is filed separately in the handoff
queue and **none was fixed** — the test forbade touching code.

1. **The iOS pushes arrived and were silent. Delivery was never the problem — presentation was.**
   Android announced all of them normally.

   | device | state | outcome |
   |---|---|---|
   | iPhone 13 Pro Max (`…0c56a19b`) | **Sleep Focus ON** | no announcement — explained by Focus |
   | iPhone 15 (`…018ab51d`) | **no Focus** | **notifications present in Mitteilungszentrale, but no banner and no sound** |

   Thomas, verbatim: *"I see the notifications on the iPhone 15 under Mitteilungszentrale … so they
   are arriving, some setting makes them NOT go PING!"*

   So the chain is intact end to end: BHNM → middleware → APNs → device → Notification Centre.
   What failed is the **announcement**, which on iOS is a per-app presentation setting —
   *Deliver Quietly*, or Sounds off, or Banners set to None. *Deliver Quietly* is the likeliest and
   is set with two taps directly from a notification, which makes it easy to enable by accident and
   invisible afterwards.

   **The product finding, and it is a real one:** a paging app can be demoted to silent delivery by
   an accidental swipe, and **BeNeM has no way to notice or say so.** iOS exposes exactly this
   through `UNUserNotificationCenter.getNotificationSettings()` — `alertSetting`, `soundSetting`,
   `lockScreenSetting`, `alertStyle` — and the app reads **none** of them. It is the same recorded
   doctrine case as "notification permission denied at the OS level, which the app never reads",
   one notch milder: permission is granted, announcement is off, and the app's own switch still
   reads ON. **This belongs with queue item 5** (verified registration state), which already
   proposes reading `authorizationStatus`; it should read the presentation settings too, because
   *delivered but silent* is indistinguishable from *never sent* to a sleeping engineer.

   **For Thomas, on the iPhone 15:** Settings → Notifications → BeNeM — check *Allow
   Notifications*, *Sounds*, and whether the style is *Deliver Quietly*. Reporting what it says
   closes this observation.

   Established, so the deploy is not suspected: `apns.py` and `webpush.py` are **untouched** since
   before 2.15.0, and the payload already requests `"sound": "default"`.

   And the caution this session earned the hard way: `[APNs] Sent to …` means APNs returned
   **200** — Apple accepted the push. **It is not evidence that a phone announced anything, nor
   even that a human saw it.** This session reported "Sent" for three pushes while both iPhones
   stayed quiet, and did not chase it until Thomas asked directly.

2. **iOS shows a wrong incident duration** — queue item 14. Incident 29656 was 13m 09s old at
   19:55:21Z; **iOS showed 3m, the Android PWA showed 13m**, from identical data.
   `NetreoAPIService.swift:1273` falls back to `?? Date()` when `open_time` has no timezone.

3. **A stale BHNM URL on the iPhone 15** — queue item 15. It listed incident 29656 but could not
   open it (*"The request timed out."*), because the list resolves by `api_key` to the lab while
   the detail sends `X-BHNM-Target` to `vpn.hurrikap.org:8888`, an address the lab has moved away
   from.

4. **List and detail disagreed on state at the end of the run** — iOS list showed `OPEN` with one
   green alarm while the detail screen showed `CLOSED`, with the middleware saying `CLOSED`
   throughout. **Not diagnosed**: it is either a stale list that had not refetched, or
   `NetreoAPIService.swift:1219`'s `incidentData["incident_state"] as? String ?? "OPEN"` firing.
   The discriminator is a pull-to-refresh, which was not performed before this file was written.
   Recorded as open.

## A process note on this session

Two edits to the handoff queue during this test reported success and **wrote nothing** — the
anchor text did not match and the success message was not conditional on the result. Items 13, 14
and 15 were claimed as filed while absent, and the priority line referenced an item that did not

value that nobody checks is how a no-op stays invisible* — committed by the tooling used to write
that documentation. Subsequent edits were verified by re-reading the file.
