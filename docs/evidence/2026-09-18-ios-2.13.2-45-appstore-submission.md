## What was verified, and how

### On the exported IPA — the checks that replace a device run

The archive is signed with the **development** identity and only the distribution re-sign at export
flips the push entitlement, so the archive's own entitlements are not the shipped ones. The IPA was
unpacked and read directly rather than inferred from build settings:

```
aps-environment        production          <- the .xcarchive itself read "development"
get-task-allow         false
beta-reports-active    true
application-identifier 8L27BJGYXP.com.tstolt.benem
Authority              Apple Distribution: Thomas Stolt (8L27BJGYXP)
CFBundleShortVersionString  2.13.2
CFBundleVersion             45
find Payload/BeNeM.app -name "*.xctest"   ->  0
```

The `aps-environment` check is the one that mattered: **`AppDelegate.swift:128-132` is the only
behavioural Debug/Release fork in the app**, sending `environment: "sandbox"` under Debug and
`"production"` under Release, matched by `BeNeM.entitlements` (`development`) and
`BeNeM.release.entitlements` (`production`). Had the re-sign not flipped it, a production-signed
binary would have registered against the wrong APNs host and nobody would have found out until a
page failed to arrive.

The `.xctest` check exists because `71b4f92` added a unit-test target this release. It is absent
from the shipped bundle.

### Build-configuration audit of the changed code

Every file changed since the shipped store build (`36a0583..HEAD` on `ios/`) was grepped for
`#if` / `DEBUG` / `RELEASE` / `_isDebugAssertConfiguration` / `targetEnvironment`:

```
Models/Diagnostics.swift      0 hits
Models/ServerDraft.swift      0 hits
Views/DiagnosticsView.swift   0 hits
Views/ServerConfigView.swift  0 hits
BeNeMTests/ServerDraftTests.swift  0 hits
```

**The changed code has no build-configuration branches.** The whole save-and-probe path lives in
`ServerConfigView.swift:316-500` and compiles identically under both configurations. The other 28
`#if DEBUG` blocks in the app are `print`, `UserDefaults` debug keys and debug text files — none
alters control flow, and all are stripped from Release.

`AppDelegate.swift` is **byte-identical to the shipped store build**: `git diff 36a0583..HEAD --
ios/BeNeM/AppDelegate.swift` is empty. So the production APNs registration path in build 45 is the
same code as in build 36, whose four production tokens are live in the middleware's
`device_tokens`. That path is proven by the app in the store — not by these bytes.

## NOT VERIFIED

| thing | why |
|---|---|
| **Any on-device run of build 45** | no device has run this binary. Submitted straight to review without a TestFlight install, by Thomas's decision |
| **Release optimisation level** | Release compiles `-O`; the field-verified build 44 is Debug at `-Onone`. The changed code has no configuration branches, so **the residual gap is optimisation level only** — but a miscompilation or an optimisation-sensitive bug is precisely what a device run would catch and reasoning will not |
| **The production APNs path in these bytes** | argued from `AppDelegate.swift` being identical to shipped build 36, not observed on build 45 |

**The residual gap is optimisation level only.** That sentence is the honest summary and it is also
the limit of the claim: it is a conclusion from a grep, not from a running app.

**CONFIRMED 2026-09-19 — the inference below was right, and the mechanism is now observed
directly.** Installing 2.13.3 (46), a Debug build, onto the 13 Pro Max produced this in the
middleware log:

```
09:45:31,694Z [Register] Token saved: ...10882c55 for iPhone (APNs: production)   <- the OLD app
09:49:04,299Z [Register] Token saved: ...10882c55 for iPhone (APNs: sandbox)      <- 2.13.3 (46)
```

**The same token, declared two different environments** — and `device_tokens` stayed at **5 rows**,
which proves the token string is byte-identical rather than merely similar, because `save_token`
is `INSERT OR REPLACE` keyed on the token and a different value would have added a sixth row. The
row now reads `sandbox`.

So the build that was on that phone before 2.13.3 **held a development-entitlement (sandbox) token
and declared it `production`**, which is exactly why it answered `400 BadDeviceToken` 43 times on
2026-09-18 at the production host. With the environment declared correctly it delivered first
time: `10:10:18,169Z [APNs] Sent to ...10882c55`.

**Both halves of the inference therefore hold: the field test was closer to the store build than
recorded above, and push on that install was never functional.** What is still *not* established
is how build 44 came to be installed that way — the mechanism is confirmed, the provenance is not.

## What this record deliberately does not say

It does not say the Release build was smoke-tested on device. The original plan for this release
had that wording ready and it would have been false. A deploy record that claims a check nobody ran
is the failure the root `CLAUDE.md` names four times over — a green affordance on a fact never
confirmed. Recording the absence costs nothing today and is the only thing that will be worth
having if build 45 misbehaves.

**Still available, and cheap:** build 45 reaches TestFlight on its own once App Store Connect
finishes processing, because it is the same binary. Installing it and running the three save-flow
checks takes minutes and does not disturb the review. Carried into the handoff §(e) as an optional
item rather than a blocker.

---

## Rollback

There is no rollback for an App Store submission. The store build until this one is approved
remains **2.13.1 (36)** — the build whose manual add/edit of a server is broken against the rotated
`PROXY_TOKEN`, which is the entire reason for shipping. If build 45 is rejected or found bad, the
position is the status quo: QR and deep-link import still work on 36
(`DeepLinkHandler.swift:127-144` saves with no probe), so nobody is locked out of the app.
