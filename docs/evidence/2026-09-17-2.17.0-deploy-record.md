## What this deploy does NOT close — read this before filing a bug

**2.17.0 binds `api_key` clients. It does NOT close the operator-token gap, which is
pre-existing.**

`PROXY_TOKEN` and `WEBHOOK_SECRET` hold the **same value** on this deployment (fingerprint
`95e54469`), which is also the `webhook_secrets` entry seeded on **all four servers**. So the
shared push secret *is* the operator token, and the operator token is exempt from binding by
ruling. A holder of that secret — four phones, every onboarding QR code, Steve, Luiz — still
reaches every configured server, and on the cached routes still reads their data using their own
stored key.

This was equally true on 2.16.0 and before. 2.17.0 neither causes it nor fixes it. `check-env.sh`
has flagged it since 2026-09-15 and still does:

```
── Checking for reused credential values ──
  ERROR: PROXY_TOKEN and WEBHOOK_SECRET have the SAME value
```

Sizing of the fix is in §4 below — it is **smaller than previously written**.

## A complaint from Steve or Luiz is probably this change working

**A client configured with a mismatched target — one server's `api_key`, another server's URL —
worked on 2.16.0 and gets a **403** on 2.17.0.** That is the defect surfacing, **not a
regression**: such a client was already sending its key to someone else's server.

Thomas can only exercise his own clients (iPhone 15, iPhone 13 Pro Max, Android PWA). **If Steve's
or Luiz's client is mismatched it will break and nobody here will see it until they say so.**
Before treating any such report as a 2.17.0 bug, read
`specs/2026-09-17-key-target-binding-design.md` §5, then:

```bash
grep 'not owned by this key' /root/BeNeM/middleware/logs/middleware.log
```

**A hit names the client by `User-Agent`.** The remedy is to re-import that client's connection so
its key and its URL belong to the same server — not a rollback.

## 4. CORRECTED SIZING of the next item — `PROXY_TOKEN` ≠ `WEBHOOK_SECRET`

**Previously written as "rotation, deferred, large blast radius — touches benem:// links, QR codes
and four phones." That was wrong, and the error was attributing `WEBHOOK_SECRET`'s blast radius to
`PROXY_TOKEN`.** Thomas's correction, verified read-only below.

### The contradiction is settled: `.env.example:86` is stale

`.env.example:86-87` says `PROXY_TOKEN` is *"embedded in generated `benem://` links, sent by the
iOS app as `X-Proxy-Token` on every BHNM API proxy request."* **It is not, and has not been since
2026-09-15.** `benem-admin/main.py:236-249` builds the QR payload and says so in the code:

```python
"push_secret":    push_secret_for(server),
# proxy_token deliberately NOT included. No client ever read it — neither
# DeepLinkHandler.swift nor pwa/src/lib/qr-parser.ts mentions the field —
# so it was a credential encrypted into every onboarding link for nothing …  (2026-09-15)
```

Confirmed on the consuming side: `grep proxy_token` across `ios/` and `pwa/` returns **nothing**.
`DeepLinkHandler.swift:59,217` reads `push_secret`; `pwa/src/lib/qr-parser.ts:71` reads
`push_secret`. **The QR carries `api_key` and `push_secret`. It does not carry `PROXY_TOKEN`.**

### So: nothing uses `PROXY_TOKEN` as `PROXY_TOKEN`, except one server-to-server call

| holder | what it sends | effect of changing `PROXY_TOKEN` |
|---|---|---|
| iOS runtime — `ContentView.swift:198` → `NetreoAPIService.swift:57` | the BHNM `api_key` | **none** |
| PWA — all five API modules | `config.apiKey` | **none** |
| onboarding QR / `benem://` | `api_key` + `push_secret` | **none** |
| `benem-admin` → `/internal/cache/reload` (`benem-admin/main.py:409`) | `PROXY_TOKEN` | **none** — both containers read the same `.env`, verified: both report fingerprint `95e54469` today |
| iOS **Test Connection** — `ServerConfigView.swift:309` | `draftPushSecret` | **401**, because it only ever worked by the two values being equal |

**Leading option, as Thomas's hypothesis — verified but NOT executed:**

> Change `PROXY_TOKEN` to a fresh `openssl rand -hex 32`. **Leave `WEBHOOK_SECRET` alone.** One
> line in `.env` plus a recreate of `benem-middleware` and `benem-admin`. **No phone changes, no
> QR reissue, no BHNM Action change.** Cost: iOS Test Connection returns 401 until the app is
> fixed to send the api_key — a diagnostic button that was only ever working by accident.

That is a config change with one visible casualty, not the four-phone rotation it was filed as.
It also converts the binding exemption into something that deserves the name: after it, the
operator token is held by the operator, and `OPERATOR TOKEN selected` in the log means what it
says. **(e)1 — the strength of the api_keys themselves, Luiz's 9 characters and Steve's
third-party server — is a separate and still-open item.**

**Nothing was rotated. Read-only.**

## 5. EXECUTED — `PROXY_TOKEN` rotated, 2026-09-17T14:26Z

force-recreated at **14:26:57.414Z**, `RestartCount=0`. No code change, no version change — still

The new value was generated **on the VPS** and never left it. Rollback is a file copy:
