## FINDING — a PWA deploy does not reach an open browser

**The browser still ran 0.14.1 after the deploy**, through a full navigation, while the server was
serving 0.16.3. Caught because the Settings screen prints the version.

`src/sw.ts` calls `precacheAndRoute(self.__WB_MANIFEST)` and **nothing else** — no
`self.skipWaiting()`, no `clientsClaim()`. With `strategies: 'injectManifest'`, `registerType:
'autoUpdate'` does not supply them, so the new service worker installs and then **waits until every
tab and installed window for the origin is closed**. Until then the old app is served from
precache.

**This is pre-existing behaviour, not caused by this deploy, and reverting would not change it.**
It matters operationally: **a PWA user can keep running a version for as long as they never fully
close the app**, which on an installed Android PWA can be a long time. Deciding whether to add
`skipWaiting`/`clientsClaim` — and what that does to a session mid-use — is its own change and is
**not** made here.

## NOT verified — and why

The new panels and the verified / wrong-key paths were **not** exercised in a browser. Two reasons,
both recorded rather than worked around:

1. The desktop browser is serving the old app, per the finding above.
2. **`benem.hurrikap.org` does not resolve on this LAN's resolver** — `dig +short` returns nothing
   locally while public resolvers return the VPS correctly. Chrome loaded the site twice and failed
   three times in the same minutes. That is the open LAN-DNS item, and it makes browser
   verification from this machine unreliable rather than merely awkward.

The code paths themselves are covered by the PWA suite (413 passing, including the verdict and
both PIN branches), and the strings are confirmed present in the served bundle. **What remains
unproven is the rendering, which needs a browser that has actually picked up 0.16.3.**
