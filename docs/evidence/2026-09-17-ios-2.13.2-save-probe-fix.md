# iOS 2.13.2 (37) — the save probe sends the api_key, and 403 stops lying

**Built, NOT released.** No TestFlight, no App Store. The only person who can test the save flow
is the one holding a phone.

**Cause and blast radius:** `docs/evidence/2026-09-17-2.17.0-deploy-record.md` section 6.

---

## 1. The fix

`ServerConfigView.swift` — the probe behind **Test & Save** (add) / **Save** (edit) now sends
`draftApiKey` as `X-Proxy-Token`, matching the runtime path at `ContentView.swift:198` →
`NetreoAPIService.swift:57`. It previously sent `draftPushSecret`, which authenticated only
because the deployment had `PROXY_TOKEN == WEBHOOK_SECRET`.

**Dropping the header was rejected, by ruling and by the evidence**: an absent `X-Proxy-Token`
raises 401 in `_verify_proxy_token` for its own reason (`main.py:185-187`), so removing it fixes
nothing. Sending the api_key is the only option that makes the probe behave like the rest of the
app.

## 2. 401 and 403 no longer share a message

Before, both said *"Check your API key and PIN."* Once the api_key is the proxy token they mean
different things, and for half the cases that sentence named the wrong field:

| status | what it now means | message |
|---|---|---|
| **401** | the api_key is wrong | unchanged — *"HTTP 401: Check your API key and PIN."* |
| **403** | the middleware refused this BHNM URL for this key — wrong URL, or a server this key does not own (2.17.0 binding) | *"Server not allowed … Check the BHNM URL … The API key and PIN are not the problem."* |

A 403 here is now a **likely** outcome, not a theoretical one: it is exactly what a
mismatched-target client gets, which is the case section 5 of the design note says to expect from
other people's clients.

## 3. RAISED, NOT BUILT — "Save" discards the edit when the probe fails

`saveConnection(...)` is called in exactly one place, inside `case 200` after the body parses as
HA status. **Any** probe failure — a 403, a typo'd URL, a tunnel dropping for two seconds —
throws away everything typed.

**The PWA already does the opposite**, deliberately: `ServerForm.tsx:102` calls `onSave` outside
the try/catch, under the comment `// Save regardless of test result`. So this is also a
platform-parity gap, and iOS is the outlier.

**Size: the code move is ~5 lines. The decision is not.** Three things have to be settled first,
and none is mechanical:

1. **"Test & Save" promises a gated save.** In add mode the label says the test comes first. Save
   an unverified connection and the label is a lie; keep discarding and the button is hostile.
   Either the behaviour or the label changes.
2. **A saved-but-unverified connection must not look verified.** The root `CLAUDE.md` doctrine
   applies directly: three states, and the unverified one gets its own appearance. Today a saved
   connection renders exactly one way. Saving unverified connections without that work would add a
   fifth instance of the failure the doctrine exists for.
3. **Edit mode and add mode may deserve different answers.** Losing an edit to an existing,
   working connection is pure damage; refusing to add a brand-new one that has never answered is
   arguably correct.

**Recommendation: worth doing, not trivial, and it needs a ruling on 1 and 2 before any code.**
Not built here.

### 6a. The 403 message drops its last sentence

*"The API key and PIN are not the problem."* Removed on Thomas's call, and I could not justify
keeping it. It was written to counter the old wrong wording, but the message already says **check
the BHNM URL** — a trailing negation about fields the user was not asked to touch only invites
doubt about them. The correction belonged in the fix, not in the sentence.

### 6b. Save is no longer greyed out when nothing has changed

`saveDisabled` carried `|| (!isAddMode && !hasChanges)`. The field test found what that costs:
after a failed probe, editing the bad URL **back to the correct one** makes `hasChanges` false, so
Save greys out — while the screen still reads **Connection failed**, and Save is the only control
that re-runs the probe. The user is left looking at a stale failure with no way to clear it.

**"Nothing changed" is not "nothing to do" when the button is also the retry.** The clause is
removed and `hasChanges`, which had exactly one caller, is deleted with it. Save is now enabled
whenever the required fields are filled.

This is **not** the parked question in section 3 — that one is about a *failed* probe discarding
the edit, and it is still parked. This one only restores the user's ability to press the button.

## 7. The probe moved to `incident_api.php` — 2.13.2 (39), PWA 0.15.0

**Thomas's ruling, option C**, recorded as his: A reports "verified" when BHNM bailed before it
ever looked at the key, which is the doctrine failure a fifth time; B is real work that does not
address the actual problem, which is that we were probing an endpoint the app does not use; C
exercises reachability, proxy auth, key-target binding and the BHNM credential in one call against
the endpoint the app already lives on.

### 7a. TEST 1 IS NOT DONE — and "test 1 failed" is NOT a 2.17.0 finding

The save regression test **was masked by the parse failure, not proven absent**. Every save
attempt died at `ha_status_api.php` before `saveConnection()` could be reached, so nothing was
learned about whether 2.13.2 fixed the 401. **It must be re-run on build 39.** Nobody should read
the 2026-09-18 "Parse error" screenshots as evidence about 2.17.0 or about the api_key fix.

### 7b. The probe is O(1), and that was measured, not assumed

BHNM checks the credential **before** the method, so a deliberately unsupported method answers the
only question the probe asks — *is this key good* — in a constant-size reply:

| request (direct to BHNM, 2026-09-18) | response | bytes |
|---|---|---|
| correct key, `method=benem_connection_check` | `{"result":"error","detail":"Method not supported."}` | **51** |
| wrong key, same method | `{"result":"error","detail":"Password failed."}` | **46** |
| no key | `{"result":"error","detail":"Password is required."}` | 51 |
| correct key, `method=getincidents` | full incident list | 1921 at **n=9** |

**`getincidents` cannot be bounded.** `limit=1` and `count=1` were both tried and both returned the
identical 1921 bytes — the parameters are ignored. So the cost is linear: **~209 bytes per
incident, about 204 KB at n=1000**, to answer a yes/no question. That is precisely the shape of
cost this project spent 2026-09-16 measuring in the incident-cache model, and it is not
reintroduced here.

The verdict rule is therefore: **a password error is the one failure**; any other BHNM reply proves
the credential was accepted; a body with no `result` key is not a BHNM API response at all and is
reported as such, naming the BHNM URL as the thing to check.

### 7c. The PWA is fixed the same way — parity, and one fewer knowing doctrine failure

`ha-status.ts` previously swallowed a parse error and returned `{role:'unknown'}`, commented *"A
parse error on a reachable server still means the connection works"*. It does not: BHNM returns
those **before** it looks at the credential, so that path reported a verified connection it had
never verified. `testConnection` now runs the same `incident_api.php` probe with the same verdict
rule, and a parse error is a failure.

Three tests were added for the verdict, including one that feeds in the exact PHP-serialized body
this bug produces. PWA suite **408 passed**, `tsc --noEmit` clean. `npx eslint` could not run —
the installed ESLint is v10 and the repo has no `eslint.config.*`, a pre-existing gap unrelated to
this change.

## 8. Three outcomes, and a confirmation that names what it verified — 2.13.2 (40), PWA 0.16.0

**All three tests passed on build 39**, so the save regression is closed: test 1 finally ran.

### 8a. The verdict rule was too generous, and the failure ran the wrong way

The rule *"a password error is the one failure, any other BHNM reply proves the key was accepted"*
treated an unrecognised reply as a **pass**, and hung the entire verdict on BHNM's exact wording of
`Password failed.`. Had that string changed in a future release, **a wrong key would have read as
a good connection** — the failure running in the dangerous direction.

**Three outcomes now:**

| outcome | matched on | result |
|---|---|---|
| **verified** | `result: "completed"` — structural, BHNM did work so the key was accepted — **or** a `detail` containing the word **method** | saves, confirmation shown |
| **authentication failed** | `detail` containing **password** or **credential**, checked FIRST so an auth error can never be read as anything else | does not save, quotes BHNM's own words |
| **inconclusive** | everything else, a body with no `result` key included | **does not save**, says plainly that the connection is not verified, shows what came back |

**What is matched, and why that is the best available.** BHNM's API carries **no error code** —
only `result` and a human `detail` — so a string match somewhere is unavoidable. What changed is
where it can fail. `result: "completed"` is structural. The **method** match is the narrowest
meaningful structure available: the method is the thing we deliberately got wrong, and BHNM checks
the credential *before* the method, so **any** complaint about the method necessarily happened
after the key was accepted. Matching the word rather than the sentence covers all three method
complaints observed on 2026-09-18: `Method not supported.`, `Missing method in your request.` and
`Missing required information for this method.`

**A rewording now degrades to "could not verify", never to a false pass.** Two tests pin this,
including one that feeds in `Invalid credential supplied.`

### 8b. An inconclusive result does not save — and why

Because the save *is* the claim. iOS gates saving on the probe, so a saved connection means
"verified". Saving on inconclusive would rebuild exactly the false-verified state this work just
removed from the PWA.

**The cost is real and is stated rather than hidden:** if BHNM rewords its way out of every branch,
saving stops working, which is what `ha_status_api.php` just did to us. Two things keep that
recoverable — the alert **shows the raw body**, so the cause is visible rather than mysterious,
and the success match is deliberately broad, so a rewording would have to avoid the word *method*
entirely.

### 8c. The platforms differ, and the reason is structural

iOS gates the save on the probe, so its confirmation can assert verification. **The PWA saves
regardless** (`ServerForm.tsx`, `// Save regardless of test result`), so it cannot claim the same
thing on failure. Same sentence where the same thing is true; different where it is not:

| | iOS | PWA |
|---|---|---|
| verified | *"Connection verified — BHNM is reachable through the middleware and accepted the API key."* then returns to Settings | same sentence in the green panel |
| not verified | alert, **nothing saved** | red **"Not verified"** panel, plus *"The server was saved anyway, but this connection is not verified."* |

The PWA's extra line exists because a server sitting in the list unverified is precisely the state
the doctrine says must not be drawn like a verified one. Whether the PWA should keep saving
regardless is the still-parked question in section 3.

**Verified:** iOS `BUILD SUCCEEDED`, installed, device reports **2.13.2 / 40**. PWA **411 passed**,
`tsc --noEmit` clean. **Not verified:** the new confirmation and the inconclusive alert have not
been seen on a phone.

### 8d. Wording, 2.13.2 (41) / PWA 0.16.1 — strings only, no verdict change

**The PIN applies to SaaS servers only**, so neither message may imply it is always relevant.

**Confirmation:**

> **Connection verified**
> BHNM is reachable through the middleware and accepted the API key.
> Not covered by this test: push notifications and the PIN on SaaS servers.

**Authentication failure — the conditional form, which was cheap.** BHNM never says *which*
credential it rejected, so the app must not either. It quotes BHNM, then points at the right field
using what the form already knows:

> BHNM rejected these credentials: "*BHNM's own words*"
> — a PIN was entered → **Check the API key and the PIN.**
> — no PIN was entered → **Check the API key. SaaS servers also require a PIN.**

`draftPin` on iOS and `config.pin` in the PWA were already in scope at both call sites, so this
was three lines per platform rather than the flat fallback wording. It removes the conditional
from the user's side entirely: nobody has to work out whether they are on SaaS.

**Tests asserting on wording:** none existed — the PWA tests asserted only on `error.kind`. Since
the guidance is now a **branch** rather than a constant, three were added: one pinning each PIN
branch, one pinning that BHNM's words are quoted rather than paraphrased. PWA **413 passed**.

**No verdict logic changed.** The three outcomes and what they match on are exactly as in 8a.

### 8e. CORRECTION — the confirmation understated what it verified. 2.13.2 (43) / PWA 0.16.3

The confirmation carried *"Not covered by this test: push notifications and the PIN on SaaS
servers."* **The PIN half was false.** Thomas: the PIN *would* be tested, otherwise a SaaS instance
could not be connected to at all.

He is right, and the code says so. The probe sends `pin` whenever one is entered, and BHNM checks
credentials **before** the method — the same ordering the whole probe design rests on. A wrong PIN
therefore fails this probe exactly as a wrong key does.

Two things follow, and both are now done:

1. **The sentence is gone**, on both platforms, rather than half-repaired.
2. **"API key" became "credentials"**, which is the accurate word for what was checked: the key
   always, plus the PIN wherever one applies.

> **Connection verified**
> BHNM is reachable through the middleware and accepted the credentials.

**This is the doctrine pointed the other way.** Every earlier instance this week was the app
claiming health it had not verified. This one was the app **disclaiming** something it *had*
verified — still telling the user something with no basis, still a sentence written from
assumption rather than from the code. A comment at the call site records why the PIN is not listed
as uncovered, so it does not get helpfully added back.

The authentication-failure guidance is unchanged and remains correct: BHNM never says which
credential it rejected, so the app quotes BHNM then points at the right field using whether a PIN
was entered.
